# 路线图（P1–P3）

P0（Web MVP）已完成，现状见 [Web 界面](web-ui.md)。
本文件记录后续优化项：**先消除交付风险 → 再提升准确率 → 最后扩场景**。
每项都给出目标、做法、验收和估算，便于按需取用。

## 优先级原则

1. **先可用**：导出格式、可视化、服务化，让结果能被业务直接消费。
2. **再准确**：交叉校验、表格结构、异常输入，降低静默错误。
3. **后扩展**：RAG、多用户、多后端。
4. 每项必须有本机可验证的验收标准。
5. 不引入云服务，不增加前端构建步骤。

## P1 — 生产可用

### P1-1 表格导出 CSV / XLSX

**目标**：每张表导出为可计算的数据，而不是只有 HTML。

**为什么**：业务方要的是 Excel/CSV；现在是 HTML `<table>`，还要手工二次处理。

**做法**
- 从 IR 的 `type=table` 块解析 HTML（必要时回退原始 OTSL）。
- 每个文档输出 `stem.tables.xlsx`：每张表一个 sheet；另出 `stem.tables.zip`（每表一个 CSV）。
- 空单元格保留列；合并单元格先按“展开为重复值”处理，span 精确还原放 P2-2。

**验收**：扫描表格 PDF 导出的 xlsx 与页面行列一致；空单元格不丢列；表格标题作为 sheet 名或首行。

**估算**：1–2 天。

### P1-2 DOCX 导出

**目标**：输出可编辑的 Word 文档，标题层级、段落、表格保留。

**做法**
- `type=title` → `Heading 1/2`（按字号或层级推断）；
- `type=text` → 段落；
- `type=table` → `python-docx` 表格；
- 公式以 LaTeX 文本插入（不嵌入 OMML）。

**验收**：docx 打开后标题有层级、表格可编辑、中文不乱码。

**估算**：1 天。

### P1-3 bbox 叠加 + confidence 可视化

**目标**：在页面上画出每个 block 的框，颜色按类型/置信度区分；点 block 定位。

**为什么**：VLM 的错误是静默的；可视化是“少人工复核”下最重要的排查手段。

**做法**
- 解析时按需生成页面缩略图（120 DPI JPEG）到 `output/pages/`。
- API：`GET /api/jobs/{id}/pages/{n}.png`。
- 前端 canvas 叠框：`title/text/table/formula/figure` 不同颜色；低 confidence 或 high 告警加粗。
- 点击 JSON 树中的 block，滚动并高亮对应框。

**验收**：任意失败/告警页面能在 3 秒内定位到具体区域；框与实际内容对齐。

**估算**：1–2 天。

### P1-4 KIE 模板 + 字段校验规则

**目标**：按单据类型保存字段模板，自动校验格式与跨字段一致性。

**做法**
- 模板：`~/.docparse/templates/<name>.json`，含 `fields[]` 与 `rules[]`。
- 规则类型：必填、正则、日期、金额、枚举、跨字段（金额 = 明细合计）、校验位（发票号/统一社会信用代码/身份证）。
- 结果写入 `meta.kie[].validation`；失败按 severity 进入告警。
- Web 参数面板可选模板，也可临时输入字段。

**验收**：发票模板能校验“价税合计 = 金额 + 税额”；日期非法/未来日期会被标记。

**估算**：1–2 天。

### P1-5 复核队列（只处理 high）

**目标**：把 `needs_review=true` 的文件集中展示，支持“接受 / 重跑 / 换模式”。

**为什么**：虽然目标是少人工，但 high 告警必须有人看一眼；集中处理比逐个翻任务高效。

**做法**
- 新增“待复核”视图：筛选 `severity=high` 或 `field_not_grounded`。
- 操作：接受并记录；region/更高 DPI 重跑；只重跑失败页（依赖 P2-7）。
- 复核结果写回 `job.json`，不修改原始产物。

**验收**：high 告警文件 100% 进入队列；处理后不再出现在待复核列表。

**估算**：1 天。

### P1-6 sha256 去重与结果缓存

**目标**：同一文件 + 同一参数不重复跑模型。

**做法**
- Key = `sha256(file) + hash(parse options) + model id + docparse version`。
- 缓存索引 `~/.docparse/cache/index.json`；命中时复制产物并秒回。
- Web 显示“缓存命中”。

**验收**：同一文件二次提交 <1 秒完成，产物字节一致。

**估算**：0.5 天。

### P1-7 解析版本记录（可复现）

**目标**：每次解析记录足以复现的元数据。

**做法**
- 写入 `Document.meta.versions`：`docparse`、git commit、Ollama 版本、模型 id、layout 模型、prompt hash、DPI/mode/参数。
- JSON 与 Web 详情页展示。

**验收**：任意历史任务能回答“用的哪个模型/哪版 prompt/什么参数”。

**估算**：0.5 天。

### P1-8 systemd 用户服务

**目标**：开机自启，崩溃自动重启。

**做法**
- `~/.config/systemd/user/docparse-web.service`，`Restart=on-failure`。
- Ollama 用同样的用户级服务，或沿用 `scripts/start_ollama.sh`。
- 日志走 journald：`journalctl --user -u docparse-web -f`。

**验收**：重启机器后 `http://127.0.0.1:8787` 可直接访问。

**估算**：0.5 天。

## P2 — 质量与规模化

### P2-1 关键字段交叉校验（PaddleOCR）

**目标**：用第二个独立引擎复核金额、日期、单号等高风险字段。

**做法**
- 对含 KIE 字段或数字密集的页面/区域，用 PP-OCRv5 再识别一次。
- 数字 token 逐位比对；不一致 → `field_disagreement`（high）。
- 只在必要时启用，避免每页翻倍开销。

**验收**：注入一个错误金额的样例能被标记；正常样例不产生假阳性。

**估算**：2–3 天。

### P2-2 跨页表格合并 / span 还原

**目标**：跨页表格合并为一张；合并单元格的 rowspan/colspan 正确还原。

**做法**
- 跨页判定：列数一致 + 表头相似 + 相邻页首尾行连续。
- span 还原：从裁块/单元格坐标推断（PaddleX 表格结构或 HTML colspan）。
- IR 中 table 块增加 `spans[]`。

**验收**：跨两页的 6 列表格导出的 xlsx 行数正确、无重复表头。

**估算**：3–5 天。

### P2-3 页眉页脚策略可配置

**目标**：整页模式默认忽略页眉页脚；票据/合同可选择保留。

**做法**
- 参数 `header_footer: ignore|keep`。
- `keep` 时对 region 模式保留 header/footer 标签；整页模式改用变体 prompt 或后处理补回。
- 记录策略到 `meta.versions`。

**验收**：同一份票据在 `keep` 下能保留页脚金额/编号。

**估算**：1 天。

### P2-4 插图 caption / 资源导出

**目标**：把文档内插图导出为图片，并生成 caption。

**做法**
- 从页面图按 figure bbox 裁剪，存 `output/assets/`。
- 用 VLM 对插图生成一句描述（可选开关）。
- Markdown 中插入 `![caption](assets/xxx.png)`。

**验收**：含 3 张插图的 PDF 能导出 3 个文件 + 3 条 caption。

**估算**：1–2 天。

### P2-5 评测面板 + 回归集

**目标**：在 Web 里上传参考 Markdown，直接看 CER/相似度；改 prompt/模型后自动回归。

**做法**
- 复用 `docparse/evaluate.py`；新增 `/api/eval` 与结果页。
- 保存回归集与历史分数；分数下降超过阈值时提示。
- 支持按文档类型分组统计。

**验收**：一次上传 10 份带参考的输出报告；能看到逐文件 CER 与均值。

**估算**：2 天。

### P2-6 异常输入

**目标**：不因单个坏文件卡住队列。

**做法**
- 加密 PDF：提示密码（Web 表单字段），或标记 `encrypted` 跳过。
- 损坏文件：捕获异常，标 `failed` 并给出原因。
- 超大文件：页数上限、流式渲染、内存上限。
- 页范围：`start-end` 参数（CLI 与 Web）。

**验收**：队列中混入加密/损坏/500 页文件，其余文件正常完成。

**估算**：1–2 天。

### P2-7 增量重解析

**目标**：只重跑失败页或改参数影响的页，不整篇重来。

**做法**
- 每页 IR 单独持久化（`pages/p0001.json`）。
- 重跑时按页合并；记录每页的参数哈希。
- 与 P1-5 复核队列联动。

**验收**：100 页文档第 37 页失败，修复后只重跑该页（<5 秒）。

**估算**：2–3 天。

### P2-8 吞吐与资源优化

**目标**：在不增加显存的前提下提高批量速度。

**做法**
- 对比 Q4_K_M / Q8_0 量化：速度、显存、准确率（用 P2-5 回归集）。
- 页面渲染与模型推理流水线化（渲染下一页时跑当前页）。
- layout 结果缓存；相同图片不重复检测。
- 控制 Ollama `num_ctx` 与 `num_batch`。

**验收**：同样 50 页，吞吐提升 ≥30%，准确率下降 <0.5 个点。

**估算**：1–2 天。

## P3 — 扩展

### P3-1 RAG chunks + 本地检索

**目标**：把 IR 切成带来源的 chunk，支持本地向量检索。

**做法**
- 按 block 边界切块（标题层级 + 表格独立成块），保留 `page/bbox/source`。
- 本地 embedding（如 bge-m3 / sentence-transformers），向量库用 sqlite-vec 或 Chroma。
- 检索结果可回溯到原页 bbox（依赖 P1-3）。

**验收**：上传 20 份文档后，问题能命中正确段落并高亮原位置。

**估算**：3–5 天。

### P3-2 插件式输出格式

**目标**：新增格式不改核心代码。

**做法**
- `writers` 注册表：`register_format(name, renderer)`。
- 第三方格式（如 JSONL、自定义 XML）通过 entry point 或本地插件目录加载。

**验收**：新增一个格式只需一个文件 + 一行注册。

**估算**：1 天。

### P3-3 多用户 / 鉴权

**目标**：仅在需要局域网/多人访问时启用。

**做法**
- Token 或账号体系；每用户独立任务目录与配额。
- 上传隔离、下载鉴权；可选 HTTPS 反代。
- 默认仍只监听 127.0.0.1。

**验收**：未鉴权请求 401；用户 A 看不到用户 B 的任务。

**估算**：2–3 天。

### P3-4 任务优先级 / 限流

**目标**：重要单据插队；防止一次提交淹没队列。

**做法**
- 优先级队列；每用户/每 IP 的并发与日配额。
- Web 显示排队位置与预计时间。

**验收**：高优先级任务在 1 个任务内被调度。

**估算**：1–2 天。

### P3-5 多推理后端

**目标**：在 vLLM / llama.cpp / Ollama 之间切换，做 A/B。

**做法**
- `backend.py` 抽象为 `chat()` 接口，新增适配器。
- 记录实际后端与版本到 `meta.versions`。
- 用 P2-5 回归集比较准确率与速度。

**验收**：同一批文档在两个后端跑分，结果可对比。

**估算**：2–3 天。

---

## 推荐实施顺序

1. **交付闭环**：P1-1 → P1-2 → P1-7
2. **可排查**：P1-3 → P1-5
3. **效率与稳定**：P1-4 → P1-6 → P1-8
4. **准确率**：P2-1 → P2-6 → P2-5
5. **复杂版面**：P2-2 → P2-3 → P2-7 → P2-4 → P2-8
6. **扩展**：P3-1 → P3-2 → P3-3 → P3-4 → P3-5

## 明确不做

- 不做公网 SaaS，不接云 OCR。
- 不引入前端构建链（保持无 Node、无 CDN）。
- 不为每种文档训练专用模型；用模板、规则和参数扩展。
- 不追求“全自动零误报”；目标是把人工集中到 `high` 告警。
