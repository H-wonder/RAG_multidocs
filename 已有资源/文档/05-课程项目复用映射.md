# 课程项目复用映射：RAG Connector Platform

> 对应课程任务书“案例二：RAG Connector Platform——知识接入与检索平台”。
> 本文回答三个问题：**哪些已有代码能直接用、课程最低要求怎么落、哪些内容不要搬。**

## 1. 先把课程要求翻译成模块

项目目标是“插件平台 + 多模态文档解析 + RAG”，不是只做 TXT/Markdown 玩具版。
下面的映射同时覆盖课程硬性要求和目标版能力：

| 任务书要求 | 目标模块 | 可复用的已有代码 |
| --- | --- | --- |
| 统一文档模型：文档标识、正文、来源 | `document_model.py` | `Document`、`Chunk`、`stable_doc_id` |
| 基础 TXT 接入（内置） | `builtin_txt` Connector | 新写（简单）；可参考 docparse `parse_text` |
| 多模态接入：PDF/扫描件/Office（内置） | `builtin_docparse` Connector | `docparse_connector.py` + `可选组件/docparse` |
| 简单关键词索引与检索（回退） | `KeywordIndex` | `keyword_index.py`（BM25，纯标准库）；切块用 `chunking.py` |
| RAG 主检索：向量 + BM25 混合 | `MilvusHybridIndex` | `milvus_hybrid_index.py`、`embedders.py` |
| 带来源的命中文本 | `Chunk.source/page/section_path/bbox` | `document_model.py` + `chunking.py` |
| 接入失败提示 | Connector 错误契约 | 参考 `docparse_connector.py` 的错误分层 |
| 独立 Markdown Connector | 独立扩展模块 | `chunking.chunk_markdown` 可直接复用 |
| Connector 契约与插件发现 | `plugin_registry.py` | manifest + adapter；核心不按类型分支 |
| 不按数据源类型增加分支 | 核心只依赖 Connector 契约 | docparse 的“IR → 统一视图”思路 |
| 多模态解析不污染平台环境 | docparse 子进程 | `DocparseConnector` 只调 CLI，不 import docparse |

## 2. 目标架构（插件平台 + 多模态 + RAG）

```text
用户 CLI / 简洁页面
  │  ingest --source txt      --path notes.txt
  │  ingest --source pdf      --path papers/
  │  ingest --source markdown --path docs/
  │  search "检索器怎么训练"
  ▼
Core（core/，运行在 rag 环境）
  ├── Document / Chunk          统一模型（document_model.py）
  ├── ConnectorRegistry         读取 manifest/config，加载 Connector
  ├── IngestService             Connector → 切块 → 去重 → 索引 → 结果汇总
  ├── IndexBackend
  │   ├── MilvusHybridIndex     dense + BM25（主）
  │   └── KeywordIndex          倒排索引（离线回退）
  └── SearchService             查询 → 命中（带 source/page/section/bbox）
  ▼
Connector 插件（只依赖公开契约）
  ├── builtin_txt               TXT（核心内置）
  ├── builtin_docparse          PDF/扫描件/Office（核心内置，子进程调用）
  └── connector_markdown        Markdown 目录（独立扩展，不改核心）
  ▼
外部组件
  ├── docparse conda env        docparse CLI / Parser
  ├── Ollama                    xiaomi-ocr-0（扫描页）
  └── Docker Milvus             milvus-standalone:19530
```

依赖方向：

```text
CLI ──► Core ──► Connector 契约（Protocol / manifest）
          │              ▲
          │              ├── builtin_txt
          │              ├── builtin_docparse ──subprocess──► docparse env
          │              └── connector_markdown（独立扩展）
          ▼
      IndexBackend ──► Milvus / 关键词倒排
```

三条硬边界：

1. 核心**不能** import 独立扩展的实现，也不能 import docparse 的内部模块；
2. 核心**不能**按 `source_type` 写 if/else，只能按注册名查找 Connector；
3. Connector 只产出 `Document`（或 `Document + IR`），不直接操作索引。

## 3. Connector 公开契约（建议）

```python
# core/contracts.py
from dataclasses import dataclass
from typing import Protocol

@dataclass
class ConnectorConfig:
    source_type: str          # "txt" | "markdown" | ...
    path: str                 # 文件或目录
    options: dict             # Connector 专属配置，核心不解释

@dataclass
class ConnectorError:
    code: str                 # FILE_NOT_FOUND / EMPTY_SOURCE / PARSE_ERROR ...
    message: str
    source: str = ""

class Connector(Protocol):
    name: str
    def load(self, config: ConnectorConfig) -> list["Document"]:
        """成功返回文档列表；失败抛 ConnectorLoadError。"""
```

错误约定：

| 情况 | 行为 |
| --- | --- |
| 路径不存在 | `FILE_NOT_FOUND`，CLI 退出码非 0 |
| 目录为空 / 没有匹配文件 | `EMPTY_SOURCE`，返回空列表 + 明确提示 |
| 单个文件不可读 | 记录该文件的错误，继续处理其他文件；最终报告部分成功 |
| 编码错误 | 用 `errors="replace"` 读取并记录 warning，不静默丢文件 |
| Connector 抛未知异常 | 核心捕获，转成 `CONNECTOR_ERROR`，保留原始信息 |

关键：**核心不按 source_type 写 if/else 分支**。TXT 是内置 Connector，Markdown 是
独立扩展，两者走同一个 `load()` 入口。

## 4. 独立 Markdown Connector 怎么做

目录建议：

```text
connector_markdown/
├── manifest.json          # name/version/description/entry
├── adapter.py             # load(config) -> list[Document]
└── tests/test_markdown.py
```

`manifest.json` 示例：

```json
{
  "name": "connector.markdown",
  "version": "0.1.0",
  "description": "递归读取 Markdown 目录",
  "entry": "adapter:load",
  "enabled": true
}
```

核心通过 `plugin_registry.PluginRegistry`（或更简单的注册表）发现它：

```python
registry = PluginRegistry(Path("connectors"))
documents = registry.run("connector.markdown", {"path": "docs"})
```

接入时核心源码不变，只增加配置：

```json
{
  "connectors": [
    {"name": "markdown", "module": "connector_markdown", "enabled": true}
  ]
}
```

验证“核心源码不变”的方法：

1. 在扩展合入前后对 core 目录做 `git diff --stat`，应为空；
2. 禁用扩展（`enabled: false` 或移除目录），系统仍能完成 TXT 导入/检索；
3. 让扩展抛错（例如传入不存在的目录），观察核心返回结构化错误而不是崩溃。

## 5. 目标版实现清单

### 核心（必须）

- [ ] `Document` / `Chunk`：`doc_id/source/content/title` 与 `text/source/page/section_path`，可选 `bbox`
- [ ] Connector 契约 + 注册表：manifest/config 发现，核心不按 `source_type` 分支
- [ ] `IngestService`：Connector → 切块 → 去重（可选）→ 索引 → 汇总
- [ ] `KeywordIndex`：中文按字/二元组，英文按词；记录 `chunk_id → 文档/来源`
- [ ] `SearchService`：查询分词 → 命中块 → 排序 → 返回 `text/source/doc_id/page/section`
- [ ] 错误模型：文件不存在、空数据源、不可读文件、解析失败、索引不可用
- [ ] CLI：`ingest`、`search`、`list`、`connectors list/enable/disable`，失败退出码非 0

### 多模态内置 Connector（目标必需）

- [ ] TXT Connector：UTF-8 / `errors="replace"`，空文件报错
- [ ] docparse Connector：PDF 原生抽取、扫描件 OCR、docx/pptx/xlsx
- [ ] 通过子进程调用 docparse，配置 `repo/python/mode/timeout`，不 import docparse
- [ ] 统一映射：`page`、`section_path`、`bbox`、`source` 进入 `Chunk`
- [ ] docparse 不可用/单文件失败时返回结构化错误，不影响其他 Connector

### RAG 检索（目标必需）

- [ ] 嵌入：本地 bge-small-zh（或 DashScope），维度与集合一致
- [ ] Milvus 混合检索：dense + 服务端 BM25，WeightedRanker 或 RRF
- [ ] 入库幂等：按 `doc_id` 先删后插，chunk id 确定
- [ ] 查询：`top_k`、按 `doc_id` 过滤、返回来源字段
- [ ] 关键词倒排作为离线回退：Milvus 不可用时可切换/自动降级，并在结果中说明后端
- [ ] `expand` / `rerank` 可选，不接就不调用外部 LLM

### 独立扩展（必须）

- [ ] Markdown 目录 Connector：递归 `.md`，按标题提取 `section_path`
- [ ] manifest + adapter，独立构建/打包，接入时核心源码不变
- [ ] 扩展自己的测试：目录读取、空目录、编码错误、与核心的集成
- [ ] 禁用扩展后 TXT/docparse/检索仍可运行

### 测试（必须）

- [ ] 正常：导入 TXT/PDF → 查询命中正确文档或片段
- [ ] 边界：空文件、空目录、不存在的路径、损坏 PDF、空 OCR 结果
- [ ] 扩展：启用 Markdown → 同一检索入口命中新资料
- [ ] 检索断言 `doc_id`/`source`/关键片段，不能只断言“返回非空”
- [ ] Milvus 集成测试可标记为 `@pytest.mark.integration`，没有服务时跳过
- [ ] 故意引入一个小错误，确认测试失败，再恢复

### 发布与协作（必须）

- [ ] Git 分支 + PR/MR + 具体 Review 意见 + 处理记录
- [ ] CI 执行构建/测试，保留一次真实成功记录
- [ ] Tag + 发行 ZIP/可运行目录 + 仓库外 `release/RELEASE.md`
- [ ] README 成员贡献与 AI 核验表

### 如果时间不够，按这个顺序降级

1. 核心 + TXT + 独立 Markdown + 关键词倒排（保底，一定能演示）；
2. 加 docparse 的 PDF 原生抽取（不依赖 OCR）；
3. 加 Milvus 混合检索（保留关键词回退）；
4. 再加扫描件 OCR / 图片（需要 Ollama，风险最高，最后做）。

## 6. 补充能力与取舍

| 能力 | 复用 | 代价 | 建议 |
| --- | --- | --- | --- |
| SimHash 去重 | `dedup.py` | 低 | 建议做，演示“重复资料不重复入库” |
| 增量入库清单 | `manifest_store.py` | 低 | 建议做，演示重复导入不产生重复块 |
| HTML Connector | 新写（stdlib `html.parser`） | 中 | 可以不选；独立扩展做 Markdown 即可 |
| 查询扩写 / 重排 | `rag_service.py` 思路 | 中 | 可选；没有外部 LLM 就明确写未实现 |
| 原文截图高亮 | `ocr_service.render_citation` 思路 | 中 | 可选；至少保留 page + bbox |
| 生成回答 | LLM | 中 | 可选；必须区分检索证据与模型输出 |
| Attu 管理界面 | Docker | 低 | 演示/排障用，不算功能 |

任务书明确说“生成回答、向量数据库和真实模型调用均为可选”“不做复杂向量检索”。
本项目把 Milvus 和 docparse 作为目标能力，但必须保留**关键词倒排 + TXT/Markdown**
这条不依赖外部服务的闭环；否则演示环境一坏就没有退路。README 要如实区分
“核心能力、目标版增强、未实现项”。

| C 索引/入口/发布 | 关键词倒排、Milvus 混合检索、SearchService、CLI、集成测试、CI、Tag/Release | CLI + 两套索引测试 + README/RELEASE |

交叉审查：

## 8. 在 README 里怎么交代已有代码

任务书允许基于已有项目演化，但要求“交代来源、既有能力和本次增量，保留历史及许可声明，
不将已有代码全部算作本组贡献”。建议写法：

```markdown
## 已有起点与本次增量

本项目参考了作者此前的多模态文档入库项目（DocFlow）中的以下代码：
- `core/model.py` 的统一文档/块模型：改编自 DocFlow 的 `document_model`；
- `core/chunking.py` 的切块算法：改编自 DocFlow 的 `chunker.py`；
- `core/dedup.py`：直接复用 DocFlow 的 SimHash 实现；
- `core/manifest.py`：改编自 DocFlow 的 SQLite 清单。

本次新实现：
- Connector 注册与配置、Markdown Connector、CLI 集成、全部测试与 CI；
- 倒排索引基于 `keyword_index.py` 改编或直接复用；
- 原项目基于 Airflow 的编排、OCR 服务、Milvus 检索未纳入本次核心范围。

来源仓库/提交：<填写实际路径或哈希>。第三方代码许可见 `THIRD_PARTY.md`。
```

同时保留 `LICENSE`、`THIRD_PARTY.md` 和原代码文件头部的来源注释。不要把已有代码
说成“本次从零实现”。

## 9. 常见踩坑

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 核心按文件后缀写 if/else | 新增扩展必须改核心，扩展机制不成立 | 统一 `Connector.load()`，核心只按注册名查找 |
| Connector 直接返回检索结构 | 换索引时所有 Connector 都要改 | Connector 只产出 `Document`，切块/索引在核心 |
| 测试只断言“结果非空” | 命中了错误文档也能通过 | 断言 `doc_id`、`source` 或关键片段 |
| 用绝对路径做 doc_id | 换机器/换目录后增量失效 | 用相对路径派生 doc_id |
| 把 Milvus 当核心 | 环境复杂、演示容易失败、偏离任务书 | 关键词索引先跑通，向量检索作为可选 |
| 直接复制 docparse/Airflow 全套 | 代码量失控，难以解释 | 只取需要的模块，明确标注来源 |
| README 不写已有代码 | 学术诚信与评分风险 | 按第 8 节模板写清楚 |

## 10. 一个可演示的完整路径

下面用 `rag-cli` 表示项目自己的 CLI 命令；conda 环境名是 `rag`，两者不是一回事。

```bash
# 1. 导入基础 TXT
rag-cli ingest --source txt --path samples/notes.txt
# 输出：imported 1 document, 12 chunks；index=milvus 或 keyword

# 2. 检索并显示来源
rag-cli search "检索器如何训练"
# 输出：
# [1] 0.87 notes.txt  §3 训练  "检索器与生成器联合优化……"
# [2] 0.61 notes.txt  §2 架构  "……"

# 3. 导入多模态 PDF（内置 docparse Connector）
rag-cli ingest --source pdf --path papers/rag-intro.pdf
# 输出：parsed 2 pages, imported 1 document, 18 chunks
#       命中带 page / section_path / bbox

# 4. 启用独立 Markdown Connector
rag-cli connectors enable markdown
rag-cli ingest --source markdown --path docs/
# 输出：imported 3 documents, 40 chunks

# 5. 同一检索入口命中新资料
rag-cli search "表格怎么切块"
# [1] 0.91 docs/chunking.md  §3.3 表格  "表格整块保留……"

# 6. 错误路径
rag-cli ingest --source txt --path missing.txt
# 输出：FILE_NOT_FOUND: missing.txt；退出码 2

# 7. 外部服务不可用时的回退
rag-cli ingest --source pdf --path broken.pdf
# 输出：PARSE_ERROR: broken.pdf（其他文件继续）
rag-cli search "检索器如何训练" --index keyword
# 输出：仍命中 notes.txt，结果中标注 index=keyword

# 8. 禁用扩展后基础能力仍可用
rag-cli connectors disable markdown
rag-cli search "检索器如何训练"   # 仍命中 notes.txt
```

这条路径覆盖了：核心场景、多模态接入、独立扩展、RAG 检索、错误反馈、
外部服务不可用时的回退，以及“接入前后结果对比”。
